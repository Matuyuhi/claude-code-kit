# now — この session の今の状況の要約

ユーザーは複数の session を並行で走らせ、しばらく離れてから戻ってくる。戻った時に scrollback を読み返さずに「何の件で・どこまで済み・何がわかり・何が残っているか」を掴めるようにする。

## 1. 材料

- この会話の context にあるものだけで書く（ユーザーの依頼・自分の tool 実行と結果・compact 後の要約）。要約のために新しい調査を始めない
- 例外は「今の状態」の実測だけ。編集したファイルや branch の話を書くなら、該当 repo の `git status --short` と `git log --oneline -3` 程度を読み取りで確認して良い（publish 済みか未 commit かを取り違えないため）
- 起動中の subagent・background task があれば、完了を待たずに「実行中」として書く。結果を予想で書かない
- compact された部分は要約からしか分からない。要約に書いてあることはそのまま書き、書いていない細部を想像で足さない

## 2. 出力の形

`explain-plainly` の基本形に沿う。見出しは下の順。

- 必ず出す: 「一言でいうと」「やったこと・できたもの」「残り・次の一手」
- 中身がある時だけ出す: 「背景」「わかったこと」「未確認・うまくいっていないこと」。型を埋めるために書かない（「なし」とも書かない）。短い session は必須の 3 つだけで終わるのが普通
- 複数段階の作業は、一言でいうとに「全 N 段階のうち何段階目か」を入れる

```
一言でいうと: <何の件の、どの段階か を 1〜2 文>

背景
- なぜこの作業をしているか（きっかけになった依頼・チケット・障害・レビュー指摘）
- 前提として決まっていること（ユーザーが決めた方針・却下された案）

やったこと・できたもの
- <成果物> — 何のため / 何が変わるか。状態（未 commit / commit 済み / push 済み / PR <フル URL>）

わかったこと
- <事実> — 根拠は 1 つだけ（実行結果・比較・該当箇所）

未確認・うまくいっていないこと
- <断定できていない点・失敗したまま・回避しただけの点>

残り・次の一手
1. <次にやること>（ユーザーの判断待ちなら、何を決めてほしいか）
```

## 3. 書き方

- 冒頭の 2 行だけで「何の件・今どの段階」が分かるようにする。時系列の操作ログにしない（やった順ではなく、今意味のある順）
- 途中で方針が変わった・やり直した経緯は、今の状態を理解するのに要る時だけ 1 行で書く。消えた案の詳細は書かない
- 「やったこと」と「わかったこと」を混ぜない。前者は成果物と変更、後者は調査で確定した事実
- 「わかったこと」に書くのは、依頼の本筋について確定した事実だけ。作業の途中で目に入った周辺の事実（無関係の未 commit 変更がある 等）は載せず、次の一手に影響する時だけその行に添える
- 「背景」に書くのは作業のきっかけと、ユーザーが決めた方針。ユーザーが元から知っている repo の構成・仕組みは書かない
- 実測していない数値・「全部見た」「使われていない」等は「未確認」の節に置く。完了と書くのは検証まで済んだものだけ
- ユーザーの検証・承認待ちのものは、やったことの状態に「確認待ち」と明記する
- PR・issue はフル URL。file:line の羅列は主役にしない（要る場合だけ成果物の行に 1 つ）
- 説明を付ける用語は、この session で新しく出てきたもの（調査で初めて登場したリソース名・略語・仕組み）だけ。ユーザーが普段使っている語（symlink・compact・PR・worktree 等）には付けない
- `**` 太字は使わない
- 長さの目安は画面 1 枚。短い session なら「一言でいうと」＋箇条書き数行で終える
- 要約を出したら止まる。頼まれていない次の作業を始めない（途中だった作業は、そのまま続ける旨を最後に 1 行書いて続行して良い）

## 4. 他 skill との関係

- 記録として残す → `journal`（この skill は保存しない。要約を見て「残して」と言われたら journal へ）
- 手元の git 差分・stash が何者か → `wip`
- 過去の別 session を探す → `sessions`
- 説明の崩れ方の点検 → `explain-plainly`
