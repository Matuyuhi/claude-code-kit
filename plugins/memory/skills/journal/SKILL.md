# /journal — セッションジャーナルの記録

セッション単位の作業記録を 1 ファイルで残す。読み手は次の自分（Claude）で、読む場面は 2 つある。

1. 再開: context 圧縮の後や別セッションで、この作業の続きをやる。「今どこまで済んでいて、次の 1 手は何か」が最初に要る
2. 再利用: 数週間後に同種の問題に当たり、/sessions で辿る。「どう調べ、何を試し、何がダメで、どう解決したか」が貼って動く粒度で要る

量を増やすこと自体が目的ではない。transcript にあるもの（会話の時系列、各ツール呼び出し、採らなかった案の網羅）は書かず、上の 2 場面で transcript を読み直さずに済む情報だけを足す。

## テンプレート

保存先: `~/.claude/knowledge/sessions/<YYYY-MM-DD>-<repo>-<slug>.md`
（日付は今日、repo は作業対象リポジトリ名、slug は内容の kebab-case）

```markdown
---
name: <ファイル名と同じ（拡張子なし）>
description: <一行要約（sessions/INDEX.md に載る。検索対象なので具体的に）>
metadata:
  type: session
  repo: <repo名>
  date: <YYYY-MM-DD>
  kind: bugfix | feature | investigation | design | ops
  status: in-progress | done
---
## TL;DR（1-3 行）

## 再開ポイント（status: in-progress の間は必ず最新にする。done なら「完了」の 1 行）
- 済み: <完了した単位を箇条書き。commit 済みなら hash、未 commit なら「作業ツリーに差分」と対象ファイル>
- 進行中: <今まさに途中のもの。どのファイルのどこまで手を入れたか>
- 待ち: <ユーザーの判断待ち・返事待ち。何を聞いていて、答えで何が変わるか>
- 次の 1 手: <再開したら最初にやるコマンドか編集。迷わない粒度で>
- 再開時の確認: <状態を確かめるコマンド（git status / 該当ファイルの grep / curl 等）>

## 問題 / 目的
<依頼の原文に近い形で。発端のリンク（Slack / Notion / PR / issue）はフル URL>

## 調査 flow（どの順で・何を見て・何がわかったか）
<短く。詳細な手順・コードは下の「使ったコマンド・スクリプト」へ>

## 原因 / 判断（採らなかった選択肢と理由も）
<ユーザーの指摘で変えた判断は、指摘の言葉ごと残す>

## 解決手順（再現可能なコマンド・ファイルパス・手順）

## 使ったコマンド・スクリプト
<貼って動く形で。40 行以下はそのまま、超えるなら要点の行だけ + 元の場所（scratchpad のパスはセッション後に消えるので、残したいものはここに写す）>

## ダメだったこと（原因つき）
<試して失敗した手順と、分かった原因。「sandbox で /dev/fd が開けない」「zsh の noclobber で > が失敗」「classifier が self-modification で拒否」等。同じ穴に 2 度落ちないため>

## 受けた指摘・差し戻し
<このセッションでユーザーから受けた修正・却下・好みの表明を、言葉ごと。/reflect の材料。ルール化は /reflect・/remember 側で行い、ここは事実の記録>

## 測った数値（測り方つき）
<判断の根拠にした数。「何を・どう数えたか」を添える。再測定できない数字は根拠にならない>

## 検証方法

## 触ったもの一覧
<ファイルパス・URL・commit・設定キー・Notion ページ。1 行 1 つ。本文に散らばっていても、ここにまとめる>

## 未解決・次のアクション
```

該当しないセクションは省略してよい（無理に埋めない）。ただし次は省略しない:

- `status: in-progress` のときの「再開ポイント」
- bugfix / investigation の「調査 flow」「解決手順」「ダメだったこと」
- ユーザーから指摘があったセッションの「受けた指摘・差し戻し」

## 手順

1. 既存ファイルを探す: `ls ~/.claude/knowledge/sessions/<今日の日付>-*` と、進行中なら `grep -l "status: in-progress" ~/.claude/knowledge/sessions/*.md`。同じ作業の記録があれば新規作成せず、そのファイルを更新する（「再開ポイント」は書き換え、他の節は追記）
2. 会話全体（圧縮後なら summary と、それ以降の会話）を振り返ってテンプレートを埋める
3. 確認を挟まずに Write / Edit で保存する（ローカルに書くだけで git で戻せる。依頼の時点で中身は任されている）。index は PostToolUse hook が再生成する。hook が無い環境では `"${CLAUDE_PLUGIN_ROOT}/scripts/rebuild-index.sh"` を実行する
4. 保存先パスと、記録した要点を 2〜3 行で報告する

### いつ更新するか

- ユーザーに頼まれた時
- 作業の区切り（commit した、PR を出した、調査の結論が出た、方針が変わった）で、セッションがまだ続く時。`status: in-progress` のまま「再開ポイント」を最新にする
- context 圧縮が近そうな時（長い調査・大量のツール出力の後）。圧縮の summary は要点を落とすので、journal 側に「次の 1 手」を置いておく
- セッションを終える時。`status: done` にし、「再開ポイント」を「完了」に畳む

### 再開する時

context 圧縮の後や新セッションで続きをやる時は、`status: in-progress` の記録を読み、「再開時の確認」のコマンドを実行して記録と実態の差（その後に進んだ・戻した）を確かめてから「次の 1 手」に入る。手元の差分・stash の棚卸しは `wip` skill。

## 品質基準

- 2 つの読み場面に要るものだけ書く。会話の時系列ログ、ツール呼び出しの列挙、採らなかった案の網羅は書かない（transcript にある）
- 貼って動く形で残す: 手順を文章に要約したものは再現できない。コマンド・スクリプト・jq 式・正規表現はそのまま
- 数値は測り方とセットで
- PR / issue / Notion ページ / Slack スレッドは番号やタイトルだけでなくフル URL で記録する（少なくとも初出時。後から読む時にリンクを引けるように。Notion はセッション中に触ったページの URL を必ず残す）
- 1 セッション 1 ファイルが基本。同一セッションで再実行したら既存ファイルを更新する。例外は、1 セッションで無関係な repo・主題を 2 つ扱った時で、その場合は主題ごとに分け、互いに `[[name]]` で繋ぐ
- 分量の目安は 80〜200 行。超えるなら主題で分けるか、「使ったコマンド・スクリプト」を要点に絞る
- 学び（ルール・慣習として今後も効くもの）はジャーナルではなく /remember・/reflect で別途永続化する。journal の「受けた指摘」はその材料
