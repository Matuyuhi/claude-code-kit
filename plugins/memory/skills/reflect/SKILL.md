# /reflect — 会話の学びを次のセッションで効く場所に残す

この会話全体を振り返り、次回以降も使う学びを抜き出して保存する。

## 書いて良い場所は 3 つだけ

`~/.claude/knowledge/`（横断メモリ）、`~/.claude/CLAUDE.md`、`~/.claude/skills/` 配下の SKILL.md。それ以外には書かない。

- plugin で入れた skill（`~/.claude/plugins/cache/` 配下）には書かない。plugin の更新で上書きされて消える

- built-in auto-memory（`~/.claude/projects/*/memory/`）に Write しない。MEMORY.md も編集しない
- プロジェクト配下の `.claude/CLAUDE.md` や `CLAUDE.md` を新しく作らない・編集しない（既にあっても触らない）。候補としても挙げない。プロジェクト固有の学びは `~/.claude/knowledge/projects/<repo名>/` に保存する

理由: 書く場所を global に絞ると、知識がプロジェクトごとに散らばらず、全セッションから読める。built-in memory はプロジェクト（クローンパス）単位でしか読まれない。knowledge は CLAUDE.md に import された目次を通して全セッションから引ける。

## 1. 何を抜き出すか

| 種類 | 拾うもの |
|---|---|
| フィードバック・修正指示 | 「そうじゃなくて」「やめて」「こうして」等の明示的な修正。Claude の提案を却下してユーザーが別の方法を取った箇所。「いいね」「それでいい」等、自明でないやり方への承認 |
| 作業スタイル・好み | コードスタイル（命名規則・構造・ライブラリ選択等）、コミュニケーション（詳細か簡潔か・確認の頻度等）、ワークフロー（ブランチ戦略・テスト方針等） |
| プロジェクト固有の知見 | アーキテクチャ上の判断とその理由、チーム固有のルールや制約、外部リソースの場所（ドキュメント・ダッシュボード等） |

残す基準:

- 具体的で、そのまま行動に移せる書き方にする（「コードをきれいに書く」ではなく「関数は20行以内に収める」）
- Why（なぜそのルールが要るか）をできるだけ含める
- コードや git log から読み取れる情報は保存しない
- 一時的・この会話限りの情報は保存しない
- 既存のルールと重複する内容は足さない。矛盾する時は新しい方を正として既存を更新する
- 学びが何も無い会話もある。無理に捻り出さない

## 2. 手順

1. 既存の CLAUDE.md を読み、構造・セクション・書き方を把握する。symlink にしている場合に備えて、実体を解決してから Read する

   ```bash
   readlink -f ~/.claude/CLAUDE.md
   ```

2. 会話全体から、1 の観点で学びを抜き出す
3. 学びごとに書き込み先を決める（下の 3）
4. 抜き出した結果を、書き込み先つきの箇条書きで簡潔に見せ、「これを保存しますか？」と確認する。承認なしに書かない
5. 承認されたものを `Edit` で追記する。`~/.claude/` 配下を別の場所への symlink にしている場合は、symlink 経由だと Edit が拒否されることがあるので、`readlink -f` で解決した実体パスに対して編集する
   - 既存のセクション構造・書き方に合わせる。合うセクションが無ければ新しく作る
   - skill に追記する時は、その skill の章立てに沿った位置に入れる
   - knowledge に保存する時は、形式を /remember skill に合わせ、保存後に `rebuild-index.sh` を実行する

## 3. 書き込み先の決め方

上から順に当てはめる。

1. 毎セッション必要な行動ルール・作業スタイル・好みか → `~/.claude/CLAUDE.md`。常時読み込まれるので、本当に毎回効くものだけに絞る
2. 既存の skill に合うか → その skill の SKILL.md。話題が特定の技術領域に閉じている場合
3. それ以外はすべて `~/.claude/knowledge/`

| 内容 | 書き込み先 |
|---|---|
| 技術領域に閉じないフィードバック・修正指示 | `~/.claude/CLAUDE.md` |
| 全プロジェクト共通の作業スタイル・好み | `~/.claude/CLAUDE.md` |
| ユーザーの属性・スキル | `~/.claude/CLAUDE.md`。詳細は `~/.claude/knowledge/global/` |
| 技術領域ごとの知見（iOS / Android / Go 等） | 自分で持っている `<platform>-guide` skill（`/learn-from-prs` で作れる）の SKILL.md |
| コメント・命名・エラーハンドリング等のコード品質一般原則 | 自分で置いたコード品質の skill。無ければ `~/.claude/knowledge/tech/` |
| その他、既存の skill に合う内容 | 該当 skill の SKILL.md |
| プロジェクト固有の慣習・状況 | `~/.claude/knowledge/projects/<repo名>/` |
| skill が無い技術領域の知見 | `~/.claude/knowledge/tech/<domain>/` |
| 横断で使う reference | `~/.claude/knowledge/global/` |

skill に合うか迷う時は `ls ~/.claude/skills/` で一覧を見て、description と内容に照らして決める。

## 4. 仕上げ

### 過去ジャーナルに書いたままの学びを回収する

この会話の学びを振り分けたら、過去のジャーナルに書いたまま skill に入っていない学びが残っていないかを見る。

```bash
audit-carryover.sh --since <1〜2ヶ月前の YYYY-MM-DD>
```

出た行のうち「ルール・慣習として今後も効くもの」を、3 の表に従って skill / knowledge に移す。ジャーナルは作業記録であって参照先ではないので、そこに書いただけの学びは次のセッションでは効かない。

毎回やる必要はない。ジャーナルを何本か書いた後の棚卸しとして走らせる。

### ジャーナルを書くかを判定する

保存が終わったら、このセッション自体が「後から手順を辿りたくなる作業」（バグ解決・複雑な調査・設計判断・障害対応 等）だったかを判定する。当てはまるなら /journal の実行を提案する。
