# explain-plainly — ユーザーに説明する時の書き方

ユーザーは説明の言い直しを頻繁に求める（過去 transcript で「わかりやすく / わからない」系の差し戻し 16 件、2026-10 時点）。差し戻された返答には共通の崩れ方があるので、書く前と書いた後にこれで点検する。

## 基本の形

1. 一言でいうと（結論を 1〜2 文。相手の問いにそのまま答える）
2. 全体像（短い図か、3 行以内の段落。登場する物と矢印だけ）
3. 根拠は 1 つだけ、具体例で（比較・実例・実行結果）
4. 次の一手（ある場合だけ。1 行）

file:line・URL・ID・設定値の羅列・条件分岐の網羅は、聞かれてから出す。

## 差し戻された崩れ方と直し方

### 1. 根拠資料の生の引用が本文を占める
- 例: 仕様書の文面・表の行をそのまま `>` で何段も引用し、結論が埋もれた →「ちょっと何入ってるかわからない」
- 直し方: 引用は要点を自分の言葉で 1 行にする。「A では X、B では Y、だから食い違っている」まで先に言い切り、原文は聞かれたら出す

### 2. 専門用語・略語を説明なしで使う
- 例: RBAC・finalizer・digest などを定義せず使った →「RBACとは」
- 直し方: 初出の用語は「〜とは、〜するための仕組み」を 1 文で添えるか、日常語に置き換える。略語は書かない方を優先する

### 3. 作業報告が「やった操作の列挙」になっている
- 例: apply 結果の表・PR 番号・次の PR の説明を並べ、何のためにやっているかが無い →「何してるかわからない」
- 直し方: 冒頭に「今何の件の、どの段階か」（例: 旧 API 廃止の 3 段階のうち 2 段階目が終わった）。各操作には「何のため・何が変わるか」を 1 文で付ける

### 4. ユーザーの理解と食い違う説明を、理解に触れずに出す
- 例: ユーザーは「token が要るからツールがある」と思っているのに、その前提に触れずに鍵の配り方を説明した →「わからない」
- 直し方: 質問から相手の今の理解を読み取り、「〜と思われがちだが、実際は〜」と前提のズレを先に解く

### 5. 短くする時に、要点を支える具体例まで削る
- 例: Slack 返信を「もっとわかりやすく」と言われて抽象的な要約に縮めたら、肝の「この拡張子なら 404 ページ、あの拡張子だけ別のエラーになる」という比較が消えて差し戻された
- 直し方: わかりやすさ ≠ 短さ。削るのは抽象論・条件分岐・留保。残すのは「見ればわかる」具体的な比較や実例。比較は箇条書き 2 行で並べる

### 6. 条件分岐を網羅して結論がぼやける
- 例:「脆弱性が実行前に発火するなら〜、実行時なら〜、ソースを読んでいないので〜」
- 直し方: 言えること / 言えないことを 1 行ずつに分け、言えないことは「未確認」とだけ書く。分岐の詳細は聞かれてから

### 7. 提案・作業に「なんのため」が無い
- 例: 「1 は develop の最新版の上に入れ直す作業です」と手順だけ出した →「1はなんのための作業？」「そのブランチを develop ベースで force push するだけで良いのでは？」。「設定値を main の値に戻しました」→「なんで戻したの」。「CI 走ってないのなぜ」
- 直し方: 提案・作業・変更のそれぞれに「何のため → 何をする → 何が変わる」を 1 文ずつ付ける。手順の列挙だけを出さない。特に「戻す・消す・外す」の操作は、それをしないと何が困るかを先に書く。目的が言えない作業は、やる前に本当に要るかを疑う

### 8. 聞かれていないことまで広げる
- 例: 仕様書を読んで「未確認点 2 つが解消、代わりに別 PR への指摘が 1 つ見つかった」と別の論点を足した →「話を広げないでくれますか」。ドキュメントの書き写しを頼まれて、指定していない場所に置いた。レビュー文面を頼まれて関連 PR の整理まで始めた
- 直し方: 返答は、直前の問いに対する答えだけで閉じる。調べる途中で見つけた別の論点・追加作業・改善案は、答えの後に「別件:」として 1 行で挙げるか、聞かれるまで出さない。成果物を置く場所・形式も、指定されたものから変えない

### 9. 「これ何？」に仕組み（経路）で答える
- 例: 「あの同期ジョブってなんでしたっけ」に「DB → 変換ジョブ → DWH」と経路で答えた →「内容は何してるやつ わかりづらい」
- 直し方: ジョブ・ツール・リソースが「何か」を聞かれたら、まず「何のデータ（中身）を、何のために」を 1 文で言う（例: 前日の注文の記録を、翌朝の売上報告のために DWH へ写す）。経路・構成要素はその後に 1〜2 行。扱うテーブル名等の中身が分かるなら具体名を添える

## 他人向けの文面（Slack 返信・PR author への説明）を下書きする時

- 相手が抱いている疑問 1 つに答える形にする。こちらが調べたことを全部載せない
- 相手が「〜では？」と疑っているなら、その疑いを否定・肯定する具体的な事実を 1 つ置く（例: 同じ「存在しないファイル」でも返ってくるものが違う）
- 1 メッセージ 3〜6 行。図や比較は ``` か箇条書き 2〜3 行
- 次の行動を頼む時は最後に 1 行で「〜して良いですか？」

## 書いた後の点検

- 冒頭 2 行だけ読んで、問いへの答えがわかるか
- 説明なしの専門用語・略語が残っていないか
- 具体例（比較・実行結果・実例）が 1 つ入っているか。抽象論だけになっていないか
- file:line・URL・ID が本文の主役になっていないか
- 「わかりやすく」と言われての書き直しなら、前回の文面から何を削り何を残したか。具体例を削っていないか
