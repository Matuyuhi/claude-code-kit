# design-approach — 設計時の検問と判断実例

初版: 2026-07-05、Fable 5 による書き起こし。

## この skill の性格（誤解防止）

- これは Fable の思考の写しではない。モデルは自分の処理過程を正確に内観できない。ここにあるのは出力から逆算した「必ず問われていた質問」であり、思考の再現ではなく検問所である
- この手順を踏んだから Fable 相当の設計になる、ではない。下限を上げる装置であって上限を作る装置ではない
- 調査してから設計する・トレードオフを言語化する・検証計画を持つ、といった一般的な美徳はここには書かない（モデルは言われなくても概ね守れている）。ここに載せるのは発火タイミングが問題になる判断だけ

## 共通検問 — 調査を終えて「さあ作るか」となった瞬間に答える

transcript 調査で特定した劣化点は能力ではなくタイミングだった: 正しい比較を「作った後」に出してしまう。以下は実装に入る前に全部答える。

回答は心の中で済ませず、計画・方針報告の出力に「検問:」として書き出すこと。理由は 2 つ: 書き出しは形骸的な通過（「分離したか？→した」）を防ぐ。そしてユーザーが読んで検証できる — この skill 自体が「誤りが安全に検出できるか」で設計されている。該当しない検問は「該当なし」と 1 語で書けばよく、長文にする必要はない。書き出しを要求される瞬間＝実装への転換点なので、セッション冒頭に読んだこの skill を「さあ作るか」の瞬間に再想起させる仕掛けも兼ねる。

1. 手段と目的を分離したか — 依頼の字面はたいてい手段。「Slack から表示名を取得して」の目的は「ファイル名を人間が読める名前にする」。目的まで巻き戻してから、目的に対して最小の手段を選び直す
2. 何も足さない案を先に潰したか — 新依存・新機構・新テーブルなしで目的を満たす案を必ず 1 つ作り、それが負ける理由を言えるか。言えないならそちらを採る（依存は負債）
3. もう解決していないか — 同種の修正 PR・既存の仕組みを先に探す。commit 履歴・ブランチ名・issue ID の突き合わせは安くて強い
4. この比較をユーザーに見せるのは今か、作った後か — 撤退コストが発生する前に選択肢を見せる。作ってから見せると「作った側」に寄った推しを出すバイアスが実際に観測されている
5. この変更が導入する新しい故障モードは何か — 修正・追加は必ず新しい失敗の仕方を持ち込む。「直る」だけでなく「新たに何が壊れうるか」を最低 1 つ挙げてから着手する
6. 足した機構・分岐・引数は、誰がいつ使うか言えるか — 「あると便利」「念のため」で足した worktree 切り替え・runtime で使えないツール機能・既存の複雑な実装の流用は、使い手と使う場面を 1 つ言えなければ落とす

## 種別ごとの追加検問

### 新規機能・画面
- 不正な状態の組み合わせを列挙したか。それは型で表現不能にできるか（実行時ガードは最後の手段）
- データの流れは一方向に読み下せるか。キャッシュ等の責務は Repository 側に閉じているか
- 既存の類似画面・類似機能の構成を確認したか（既存との一貫性 > 一般論）

### バグ修正・障害調査
- 仮説は複数あるか。1 つしかないなら、それは仮説ではなく思い込み
- 棄却した仮説と棄却の証拠を記録したか（「採用しなかった仮説」として報告・ジャーナルに残す）
- 最小修正か根本修正か、選んだ理由を言えるか（発生頻度・影響範囲・締切で判断）
- その修正は症状を消すだけで、別の沈黙する故障に変換していないか（クラッシュ → 機能が静かに死ぬ、は改善に見えて悪化のことがある）

### リファクタ・構造変更
- 今の構造の「痛み」を具体的な事象で言えるか（美意識だけなら見送る）
- 段階的に移行できる切れ目はどこか。1 PR で全部やる必要はあるか
- 「今直す」か「follow-up」か — 影響範囲・締切・相手で使い分ける（原理主義で強制しない）

### API・スキーマ設計
- 生成される client コードの型・プロパティ名を先に書き出したか（spec の命名・構造はそのまま client に現れる）
- 画面仕様をこの response で実装しきれるか。状態表現は足りるか。nullable の意味は一意か
- server に無理のある呼び方・回数を client に強いていないか

### 技術選定・依存追加
- 標準・既存依存で書けない理由を言えるか
- 撤退コスト: これを剥がす時に何を書き直すことになるか
- supply chain の確認（週間ダウンロード数・メンテ状況・typosquatting・install 時に走るスクリプト）を済ませたか

## 判断実例集 — この skill の本体。ここを育てる

手順書は暗黙知の半分しか運ばない。残り半分は実例に乗る。各実例は「状況 → 分岐点 → 判断 → 学び」で書く。

### 実例 1: 修正が新しい故障モードを持ち込み、外部レビューが捕捉した
（Android アプリ / 2026-07 / Sonnet 5 セッション）

- 状況: `shareIn` + `retryWhen` の独立スコープでリトライ枯渇後の例外がアプリ全体をクラッシュさせていた
- 分岐点: 初回修正 `.catch { Timber.e(it) }` はクラッシュを止めるが、upstream が完了して共有 Flow が二度と emit しなくなる（クラッシュ → 静かな機能死への変換）
- 実際: この欠陥は自力ではなく Copilot レビューで発覚し、方針変更になった
- 学び: 検問 5（新しい故障モード）を着手前に問えば自力で気づけた可能性が高い。同時に「独立した検証ループは実際に機能する」の実証でもある — 検問と外部レビューは二重化しておく

### 実例 2: 機構より手動運用を選んだ
（skill 集の運用 / 2026-07 / Fable 5 セッション）

- 状況: skill の自主発動率が低い問題。hook による自動 router（UserPromptSubmit / PreToolUse）と、ユーザー起動の入口 skill（/start）が候補
- 判断: hook 案は「既読管理の state が必要」「毎ターン発火のノイズ」「PreToolUse は発火が設計判断後で手遅れ」を理由に見送り。発火タイミングが正しく state 不要な手動入口を採用し、常時必要な判断基準だけは CLAUDE.md からの @import で常駐させる、と性質で配送方式を分けた
- 学び: 解決策の評価軸を「機能が多いか」でなく「発火タイミング・状態管理の要否・決定論性」に置く。「機構を足す前に 1 つを作り込む」が実際に選択を変えた例

## メンテナンス

- 育て方は実例の追記が主: /reflect・/learn-from-review の保存先としてこの実例集を使う。「上位モデルの良かった判断」「下位モデルが外した判断」の両方を対等に載せる（出所のセッション・モデルを明記）
- 検問リストへの追加は実例が 2 件以上溜まった質問だけ。実例の裏付けがない一般論は足さない（ノイズになる）
- 一律に全部の検問を適用しない。共通検問 6 つ + 該当種別 1 つ、で止める
