# code-comment-cleanup — 経緯コメント・低品質コメントの検出と整理

## 立ち位置

`code-quality-principles` はコメント品質の一次情報源（ルール）。だが生成時にそのルールを都度参照しない限り守られない — これがこのskillを作る動機そのもの。このskillはルールを書かない。diffに実際に書かれたコメントをルールに照らして事後監査する手順だけを持つ。

## 起動方法・引数

- 手動: `/code-comment-cleanup [対象] [mode=apply|detect-only] [min_confidence=high|medium]`
  - 省略時: `対象`＝作業ツリー、`mode=apply`、`min_confidence=medium`（高・中どちらも提示する完全監査）
- 呼び出し元は 必ず `mode` を明示して呼ぶ（呼び出し元が誰かをこのskill側が推測しない — 推測に頼ると「守られない」問題を再生産するため）:
  - `review-pr` ステップ2.8: `Skill({skill: "code-comment-cleanup", args: "target=PR<番号> mode=detect-only min_confidence=medium"})`
  - `commit` ステップ1.5: `Skill({skill: "code-comment-cleanup", args: "mode=apply min_confidence=high"})`（commit フローの摩擦を抑えるため高確信度のみ。中確信度以下の監査は `review-pr` 側に任せる）
  - その他任意のskill/agentから `Skill({skill: "code-comment-cleanup", args: "..."})` で呼べる。呼ぶ側は必ず `mode` を渡すこと

`mode=detect-only` は Step 7（Edit適用）を行わず、Step 6 の一覧を返して終了する。`mode=apply` は Step 6 の後、承認された項目に Step 7 を実施する。

## Step 1: 対象diffの決定

`target` 引数なし → 作業ツリーの差分（staged + unstaged。今このプロセスが動いているリポジトリの `git diff` であることを前提とする — 呼び出し元が別リポジトリ/別 checkout を指している可能性がある場合は先に確認する）:

```bash
git diff HEAD -U0
```

`target` がbranch名/commit range → その差分:

```bash
git diff <base>...HEAD -U0
```

`target` がPR番号 → `gh pr diff <PR番号>`（`-U0`相当の差分が要るなら別途 `git diff -U0` で取り直す）

差分がゼロなら「対象のコード変更なし」と一言だけ報告してここで終了する（`mode=apply` でもここで質問はしない）。

## Step 2: 判定基準のロード（MUST — 毎回 Read する）

同じ review plugin の `${CLAUDE_SKILL_DIR}/../code-quality-principles/SKILL.md` を `Read` し、コメントに関する項目（1, 2, 3, 4, 5, 6, 8, 9, 10, 11）を判定基準として使う。基準文をこのskillやレポートに複製しない — 常に原文を参照し、フラグを立てる際は「項目N該当」とだけ引用する。

Read した結果、Step 3 のカテゴリ表が参照している項目番号が原文と食い違っていた場合（項目の追加・番号の振り直しがあった場合）、そのズレを報告する。カタログと一次情報源の対応が切れると、新しい原則が検出面に現れないまま素通りする。

## Step 3: 検出（4パス — どれも省略しない）

キーワード検索だけでは拾えないものがある。Whatコメント・実装値の写経にはキーワードが無く（Pass B）、分量と語彙は行単位に見ても分からない（Pass C / D）。必ず 4 つとも実施する。

### Pass A: キーワード起点（経緯・推測・運用手順・曖昧理由）

`git diff -U0` の `^\+` 行（`+++` ヘッダは除く）のうち、コメント構文（`//`, `#`, `/* */`, `<!-- -->`, docstring 等、言語はファイル拡張子から判定）を含む行を対象に screening する:

| カテゴリ | キーワード例 | 対応する原則 |
|---|---|---|
| 経緯コメント（過去参照） | 「以前は」「旧」「元々」「変更前」「〜だったが」「previously」「used to」「changed from」「formerly」 | 項目8 |
| 作業分割の事情（作業単位への言及） | 「別PR」「本PR」「別途対応」「範囲外」「後続で」「follow-up」 | 項目9 |
| 作業分割の事情（軟らかい時間語） | 「暫定」「一旦」「とりあえず」「for now」「temporarily」 | 項目9 |
| 根拠不明の推測 | 「〜場合がある」「〜かもしれない」「〜と思われる」（直後に出典/URL/issue番号が無いもの） | 項目1, 3 |
| 過剰な一般化 | 「〜以降」「API Level」「常に」「必ず」「全ての」+ バージョン/普遍性の断定 | 項目4 |
| 運用手順の混入 | 「有効にする」「設定する」「権限を付与する」+ CI/環境変数/デプロイ関連語 | 項目5 |
| 層をまたぐ用語混入 | サーバー側ファイル内の「row」「セル」「タブ」「画面」等のクライアント UI 構造語 | 項目6 |
| 曖昧な理由付け | 「念のため」「安全のため」「一応」（try/catch, if の直前直後に限定） | 項目2 |
| 設計の選択理由（代替案との比較） | 「〜ではなく」「〜にしているのは」「〜より」「〜する方が」+ 型名/クラス名/API名。「〜という選択肢もあるが」 | 項目10 |

キーワードは表記ゆれを含めて照合する（`grep` の literal 一致で済ませない）: 語中の空白（「別 PR」「本 PR」）、全角/半角（「ＰＲ」）、英語表記（「another PR」「out of scope」「separate PR」）、送り仮名の違い。理由: 2026-08 に「別 PR 対応のため」と半角スペース入りで書いたコメントが、`別PR` の literal 照合をすり抜けた。

### Pass B: 全コメント走査（Whatコメント・実装値の写経）

Pass Aのキーワードに引っかからないものも含め、diffで追加されたコメント行を全て列挙する。各行について1行ずつ目視判定する:

- 直後のコードが自明に示す内容をそのまま日本語化/英語化しているだけか（Whatコメント、項目8）
- コメント内の具体的な値・条件式が、直後のコード中の値・条件とほぼ同一の文字列か（写経、項目6）
- 「Xすると〜してしまう / 〜に見える」形の失敗モード記述が、直前の文で既に説明済みの理由の言い換えになっていないか（項目8 の経緯コメントの変形）。判断軸は「消しても失われる情報があるか」— 唯一の理由説明なら残す、重複なら削る

「Why だから可」と自分で判断した行も一覧に出す（MUST）。Pass B の判定は主観であり、ここで握り潰すと `min_confidence=medium`（中確信度を出すための指定）が意味を失う。可と考えた根拠を添えて中確信度で提示し、採否はユーザーに選ばせる。理由: 2026-08 のセッションで `@param` の失敗モード記述を「Why だから可」と内部判断して一覧から落とし、ユーザーに「これは対象では？」と指摘された。

### Pass C: 分量（repo の既存分布と比較 — 項目11）

Pass A / B は「その行を書くべきか」を見る。書くべき内容でも量が多すぎる場合はここで拾う。主観ではなく repo の実測値と比較する。

1. repo の既存 KDoc / ブロックコメントの本文行数（空行・`*` だけの行を除く）を数え、中央値・p95 を出す
2. diff で追加された各コメントブロックの本文行数を、その p95 と比較する
3. p95 超のブロックをフラグにする。根拠には「repo 中央値 N 行 / p95 M 行 に対しこのブロックは K 行」と実数を書く

提案は削除ではなく 「どの行が余分か」の指摘にする。長いブロックはたいてい項目10（設計の選択理由）が混ざっているので、そこを最初に疑う。

目安: 数千件規模の repo でも KDoc は中央値 1 行・p95 2 行程度で、5 行超は 1% に満たないことが多い。

#### Pass C-2: 頻度（「付ける / 付けない」の割合を repo と比較）

行数だけでなく doc コメントを付ける頻度そのものも repo の分布から外れうる。1 行ずつは適切でも、新規の公開メンバー全部に付けていれば repo の中で浮く。

1. 対象パッケージの公開関数・メソッド・型の総数と、直前行に doc コメントがあるものの数を数える（Go なら `^func (\(.*\) )?[A-Z]` の直前行が `//` で始まるか）
2. diff で追加された公開メンバーについて同じ比率を出す
3. repo 比率の 2 倍以上ならフラグ。根拠には「repo N% / この diff M%」と実数を書く

提案は「どの doc を落とすか」の指摘。落とす優先順は 名前の言い換えだけの doc → What のみの doc → Why を含む doc（残す）。

目安: Go の domain model では doc 付きの公開メンバーが 2 割に満たない repo もある。そこへ新規の公開メンバー全部に doc を付けると、読めば分かるものまで付いていて浮く。

### Pass D: 語彙（repo の既存出現回数で判定 — 項目11）

硬い漢語のブラックリストを持たない（repo ごとにドメイン語が違い、固定リストは必ず陳腐化する）。repo 内の出現回数で判定する:

1. 追加されたコメント行から、2 文字以上の漢語熟語を候補として抜き出す
2. 各候補を `git grep <語>` で repo 全体から検索する
3. 自分の diff 以外の出現が 0 件 → その repo の語彙ではないのでフラグ。1 件以上 → フラグにしない
4. 根拠には実行した grep コマンドと件数を書く

判定例: 「遷移」が数百件ある → フラグにしない（ドメイン語として定着）。「契機」0 件 → フラグ（言い換え案を添える）。

語尾の不統一（同一ファイル内で「〜します」と「〜する」が混在）もここで見る。こちらは既存ファイル内の多数派に合わせる。

## Step 4: 裏取り（根拠なしでフラグを立てない — MUST）

カテゴリごとに裏取り手順と確信度の上限が違う。過去参照と未来参照は手順が逆になるので混同しない。

| カテゴリ | 裏取り手順 | 確信度 |
|---|---|---|
| 経緯コメント（過去参照） | 言及された旧実装・識別子・PR番号・設定値が現在のコードベースに存在するか `Grep` / `git grep` で確認。存在しない → フラグ（参照先消失） / 存在する → フラグにしない | 高 |
| 作業分割の事情（作業単位への言及） | Grep 不要。文面が作業分割を語っていること自体が根拠。根拠には該当語句をそのまま引用する | 高 |
| 作業分割の事情（軟らかい時間語） | 「暫定順位」等のドメイン用語として正当に使われていないかを、直後のコードと周辺の用語から判定 | 中 |
| 過剰な一般化 | バージョン/普遍性の断定に検証済みの出典があるかを判定（実際に検証された事実にも「〜以降」は現れる） | 中 |
| 層をまたぐ用語混入 | 対象ファイルがサーバー側の層かを確認したうえで判定 | 中 |
| 根拠不明の推測 / 運用手順 / 曖昧な理由付け | 主観判定 | 中 |
| Pass B（Whatコメント・写経・理由の重複） | 主観判定 | 中 |
| Pass C（分量） | repo の既存 KDoc 行数分布を実測し、p95 と比較。根拠に実数を書く | 高 |
| Pass C-2（頻度） | repo の公開メンバー doc 付与率を実測し、diff の付与率と比較。根拠に実数を書く。どの doc を落とすかは主観なので一括承認の対象外（Pass C と同じ扱い） | 高 |
| Pass D（語彙） | `git grep <語>` で repo 内の出現件数を確認。自分の diff 以外が 0 件 → フラグ | 高 |
| 設計の選択理由（代替案との比較） | 比較対象がコード中に存在しない選択肢（採用しなかった型・API）かを確認。存在しない → フラグ | 中 |

Pass C / D を高確信度に置くのは、確信度の基準が「主観か否か」ではなく grep や実数で裏取りできるか だからで、経緯コメント（grep 裏取り）と同じ扱いになる。

未来参照に過去参照の判定式を当てない（MUST）: 「別PRで対応」の類が指す作業はまだ存在しないのが正常なので、`Grep` で参照先の不在を確認しても削除根拠にはならない（逆に、存在しないことを根拠に扱うと判定が壊れる）。判定は「その記述はコードの性質か、作業分割の事情か」の一点で行う。

公認 TODO を巻き込まない: 「コードの望ましい最終状態」を述べる TODO は項目9 の対象外（原文の「公認の TODO は対象外」を参照）。フラグにするのは「今回はやらない・別で対応する」という作業事情の語りだけ。

確信度に関わらず、フラグを立てる際は根拠を一行添える（参照したファイルパス・行番号、実行したgrepコマンドと出力、または「直後のコード行がこの値と同一」等）。根拠を示せない候補はフラグにしない。

## Step 5: 安全側に倒す判定（MUST）

非対称リスクに注意する: まだ生きているWhy情報を誤って消すと、ビルドは通りテストも壊れず、誰にも気づかれない「静かな劣化」になる。

- 参照先リソースがまだ存在する場合、削除提案の対象にしない
- Whatコメントか写経か判定が曖昧なものは、削除ではなく「Whyのみへの書き換え案」を提案する（情報を失わない）
- ただし書き換え案を出す前に「消しても失われる Why があるか」を先に問う。Why が diff・周辺コード・変数名から読めるなら、書き換え案を並べず削除を第一候補にする（周囲の同種コードにコメントが無ければ、無しが repo の基準。書き換え案を何通り出しても、結局削除に落ちることが多い）
- 確信度「中」以下の項目は一括承認の対象から外し、個別確認を必須にする
- 一括承認してよいのは Step 4 の表で確信度「高」となるカテゴリのみ = Grep裏取り済みの経緯コメント（参照先消失）、作業単位への明示的言及、Pass D（repo に無い語彙）
- Pass C（分量）は高確信度だが一括承認の対象外。「長い」ことは確実でも「どの行を削るか」は主観なので、超過の指摘と削減案の提示に留めて個別に選ばせる

## Step 6: 結果の提示

`min_confidence` でフィルタする（`high` 指定時は確信度「中」の項目を検出しても一覧に出さない・カウントもしない）。フィルタ後の件数が0件なら「該当なし」と一言だけ報告してここで終了する（`mode=apply` でも質問はしない — 空の選択肢をユーザーに選ばせない）。

1件以上あれば番号付きで一覧化する:

```
N. <file>:<line> [確信度: 高/中]
   現在: `<コメント全文>`
   該当: code-quality-principles 項目<N>（<一言で該当理由>）
   根拠: <grepコマンドと出力、または参照ファイル:行、または「直後のコードと同一」>
   提案: 削除 / Whyのみへ書き換え「<書き換え案>」
```

`mode=detect-only` の場合はここで終了。Editはせず、この一覧をそのまま呼び出し元に返す（`review-pr` はこれを確信度に応じてレビュー指摘 高→Should Fix / 中→Nice to Have に振り分ける）。

`mode=apply` の場合、提示後にユーザーへ選ばせる:

1. 高確信度の項目のみ一括適用
2. 個別に選ぶ
3. 何もしない

## Step 7: 適用（`mode=apply` のみ）

承認された項目のみ `Edit` で適用する（python/sed/awk での一括置換は使わない。意図しない箇所まで書き換えるため）。削除の場合はコメント行のみ除去し、周辺コードの意味が変わらないことを確認する。書き換えの場合は提案文をそのまま書き込む。

## Step 8: 完了報告

検出件数（確信度別）・適用件数・見送り件数を1〜2行で報告する。

## 対象外（このskillが見ないもの）

網羅を主張するなら補集合を明示する。以下は「コメント行の監査」の外なので、検出されなくても漏れではない:

- 命名（項目6 の命名部分・メソッド名と責務のズレ等）— コメントではない。実装レビュー / `review-pr` の担当
- コメントの不在（項目2 の「握り潰した例外に理由を書く」等、必要なのに書かれていないコメント）— このskillは diff で追加されたコメント行を走査する設計なので、無いものは検出できない
- 既存コード（diff外）のコメント — 対象は常に diff の追加行。既存コメントの棚卸しは別途スコープを指定して行う

## 注意事項

- このskill自体は publish 操作（commit/push/PR作成/PRコメント）を行わない。Edit適用後は呼び出し元のフロー（commit skill 等）に戻す
- 対象言語のコメント構文を誤認識しない（例: 文字列リテラル中の `//` をコメントと誤判定しない）。判定に迷う行は候補から除外し、見送りとして報告する
- Pass Bを「キーワードで拾えなかったから対象なし」と省略しない。Whatコメント・写経はキーワードを持たないカテゴリであり、全走査でしか見つからない
