# コード品質の基本原則

## 1. コメントは事実に基づくこと

- コメントには検証済みの事実のみを書く
- 「〜する場合がある」「〜の可能性がある」といった曖昧な表現を使う場合、その根拠（公式ドキュメント、ソースコード、再現手順など）を自分自身が把握していること
- 根拠が不明な場合は、推測であることを明示するか、コメント自体を書かない
- スタックトレースやエラーログから読み取れる事実と、それに対する自分の解釈を混同しない

### NG例

```kotlin
// Android 14以降、moveToFront()が内部でNPEをスローする場合がある
// ↑ 公式ドキュメントやソースコードで確認していないのに一般的事実のように書いている
```

### OK例

```kotlin
// BackgroundActivityStartControllerによるバックグラウンド起動制限で
// moveToFront()が失敗した場合はクラッシュを防ぐ
// ↑ クラッシュログのスタックトレースに基づいた事実の記述
```

## 2. エラーハンドリングの理由を明確にする

- try-catchを追加する際は「なぜこの例外が発生するのか」を具体的に書く
- 「念のため」「安全のため」だけでは不十分。発生条件を特定して記述する
- catchした例外を無視する場合は、無視して問題ない理由を書く

## 3. 推測と事実を区別する

- コードレビューやコメントで、自分が確認した事実と推測を明確に区別する
- 推測に基づく修正を提案する場合は「推測ですが」「確認が必要ですが」と前置きする
- ソースコードを読んで確認できることは確認してから断定する
- ルール・ガイドを永続化する前に、ソースで挙動を必ず確認する: skill / CLAUDE.md / memory にルールを書く前は対象シンボルの実装を必ず Read / Grep で確認する。「多分こう」「だいたいこう」の推測で書かない。プロジェクトのデザインシステム(例: 共通部品の余白トークン)・ライブラリ挙動・API 仕様は、定義ファイルと利用箇所(既存実装)の両方を確認してから記述する。理由: 推測で書かれた永続ルールは後々別のセッションで「事実」として参照されるため、ミスが伝播しやすい
- 「既存の X を踏襲する」設計では、本物の実装を先に特定する（弱い検索の偽陰性を疑う）: 「既存機能 X と同様に作る」系のタスクで、キーワード検索の「存在しない」を鵜呑みにしない。弱いキーワードや検索エージェントは偽陰性を返す（よくある形: 機能名で検索して「実装は無い」と結論したが、実際は表示文字列の定数や別名のクラスとして存在していた）。定数の値・近縁機能名・ドメイン用語（表示文字列含む）など複数の切り口で探し、本物を特定してから設計する。理由: 偽の「無い」を前提に設計すると、流用できる既存実装を見落として車輪の再発明や設計のやり直しになる
- 設計文書では「設計荷重の事実」だけ即検証し、残りは未確定と明記して先送りする: 設計が全体重を乗せる事実（例: 依存するライブラリに、設計の前提にしている機能が組み込みで存在するか — 誤りなら設計ごと崩れる）は、文書に書く前にパッケージ実ソース等で確認する。一方、実装時に確認すれば直せる事実（外部 SDK の細かい API シグネチャ等）は事前検証に時間を使わず、「実装時に確定」と未確定であることを文書に明記して先送りする。理由: 全事実の事前検証は設計を止め、無検証は文書を推測で汚す。「間違っていたら何が崩れるか」で検証の優先度を決める
- 自分が書いた skill / knowledge の記述を「repo の規約」として根拠に使う前に、その記述の出典が確定済みか確認する: skill に `<!-- source: PR #N -->` とあっても、その PR がまだ open なら中間案の可能性がある。特に「PR N から採取」した設計方針は、その PR のレビューで覆りうる。open 中の PR の中間案を skill に「設計ルール」として書き、それを根拠に実装を巻き戻した後で、PR のレビューで結論が逆になり元に戻す、ということが起きうる。skill の記述と実装判断が衝突したら、出典 PR の状態（open / merged / close）と後続の議論を確認してからskill を根拠にする。理由: skill は自分が書いたものなので「ルール」に見えるが、鮮度は出典と同じでしかない

## 4. 過剰な一般化をしない

- 特定のバージョン・条件・端末でのみ発生する問題を、あたかも普遍的な問題であるかのように記述しない
- 「Android X以降」「API Level Y以上」などのバージョン情報を書く場合は、実際に確認したソースを把握していること

## 5. コメントには「コードの性質」だけを書く（運用・環境手順を書かない）

- リポジトリ/CI 設定の有効化、環境変数のセットアップ、外部サービスへの権限付与、デプロイ手順など、運用・環境の手順はコードの性質ではないので、コミットされるコード（コメント含む）に書かない。PR 説明・README・運用ドキュメントなどコード外に置く
- コードの挙動を説明するコメント（なぜこの分岐が要るか、なぜ無限ループしないか、なぜこの順序か 等）は書いてよい。判断軸は「コードが何をするか」＝書く / 「使う人が環境側で何を設定するか」＝書かない
- 理由: 運用手順をコードに埋めると、設定が変わるたびに陳腐化し、コードの読み手にはノイズになる。コメントは将来コードを読む人がコードを理解するためのもので、環境構築マニュアルではない

### NG例

```yaml
# この workflow を機能させるにはリポジトリ設定で
# 「Allow GitHub Actions to create and approve pull requests」を有効にすること
- name: Open PR
```

↑ 環境側のセットアップ手順。コードの挙動ではないので PR 説明・運用ドキュメントへ。

### OK例

```yaml
# GITHUB_TOKEN が作る PR は further workflow を起動しない（無限ループしない）
- name: Open PR
```

↑ このコードがなぜ安全に動くか、という挙動の説明。

## 6. 命名・コメントの付け方

### コメントは「実装値の写経」ではなく「何を表すか・なぜそうか」を書く

変数・条件の現在値をそのまま書き写すコメントは、コードと二重管理になり実装変更で嘘になる。そのコードが何を表すか / なぜそうなっているかを書く。

```go
// ❌ BAD: 条件式の値をそのまま写経
// 9:00〜17:59
func (m *Event) isStartedInBusinessHours() bool {
    h := m.StartedAt.Hour()
    return h >= 9 && h < 18
}

// ✅ GOOD: 何を対象とするか + なぜその境界か（理由）を書く
// 営業時間内に始まるイベントか判定する。
// 境界は問い合わせ窓口の受付時間に合わせている。
```

### メソッド名は「実際にやっていること」と一致させる（汎用すぎ / 具体すぎを避ける）

判定関数の名前が実装の責務とズレると誤解を生む。複数条件を束ねた述語は、その「概念」を表す名前にする（個別条件の名前にしない）。

- 「おすすめ記事判定（公開時間帯 + 公開状態 + 人気の書き手）」を束ねる関数 → `IsRecommended()`（概念名）が適切。`IsRecommendWithPopularAuthor()` は時間帯・公開状態も含むのに書き手しか表さず不正確
- 純粋に書き手の人気だけを見る内部判定 → `hasPopularAuthor()` のように具体名で切り出す
- 「最大値を持つ要素を返す」等、特定の対象に紐づく汎用処理は member function にする（package 関数 → レシーバ付きメソッドへ）

### 「値」と「判定器・生成器」で同じ語を使わない

`Order.DiscountRate int64`（値）と `type DiscountRate struct`（判定器）が同じパッケージに並ぶと、読み手は `DiscountRate` を見るたびに値か判定器かを文脈で判断させられる。判定器・生成器には `Resolver` / `Calculator` 等の役割語を付けて、値の語と衝突させない。

### サーバーのコメント・命名にクライアント UI 用語・画面名を持ち込まない

サーバー側のコメント・命名に `row` / 画面名等のクライアント UI 構造を書かない。UI 変更でコメントが嘘になり、層の責務も曖昧になる。「何のデータか（概要）」で説明する。

## 7. 新規実装が既存の類似実装を模倣・再現する場面では、書く前にその実装を確認する

- 新しいコード（同じrepo内の兄弟Feature・別OSクライアントの同機能・既存の同種UIコンポーネント等）が、既に存在する類似実装と同じ目的・同じ構造を持つ場合、実装を書き始める前にその既存実装を Read する
- 確認する観点は最低限3つ:
  1. 型・命名規約（既存の typealias / wrapper 型を使わず生の型を直接参照していないか）
  2. 既知のバグクラスに対するガード（二重発火防止フラグ等、既に他の箇所で踏んだ地雷を再び踏んでいないか）
  3. 副作用・挙動の一致（同じユーザー操作に対して既存実装が出しているダイアログ・トースト・計測イベント等を、新規実装が省略していないか）
- レビュー指摘を待って気づくのではなく、実装完了時点の自己チェックとして行う
- 理由: 既存実装を確認せず仕様書だけから再実装すると、既存実装が既に踏んだ地雷や、仕様書に明記されていない暗黙の挙動（企画との合意事項等）を再現できず、同じ指摘を繰り返すことになる

## 7-2. 要件が既存の前例と食い違う時は、実装前に指摘する

項目 7 で既存実装を読んだ結果、要件が指定している内容そのものが既存の慣習と食い違っていることがある。要件どおりに実装して黙って進めない。着手前に「既存の X はこうなっていますが、揃えなくて良いですか」と確認する。

例: 依頼文が一覧取得とは別に「判定用の boolean メソッドも用意する」と API を名指ししていても、既存の同種 Repository が一覧取得だけを提供していて、判定は呼び出し側で一覧から行う慣習なら、判定メソッドを足すと同じ判定の方法が 2 通りになる。キャッシュ済みで性能差も無いなら、足す前に「既存に合わせて一覧取得だけにしますか」と確認する。

要件を書く側も、その API が既存とどう並ぶかまでは確認していないことがある。要件は仕様の意図を伝えるものであって、API 設計の最終決定ではない。

判断軸: その API を消しても要件を満たすコードが書けるか。書けるなら、足す前に確認する。

### 要件文をそのままコードのコメントにしない

要件の「背景」に書かれた文言（「〜を禁止するため」等）を、そのまま model や定数のコメントに写さない。背景は「なぜこれが要るか」であって、その定義そのものの説明ではない。例えばマスタ定義に「この操作を禁止する」と書くと、禁止するかどうかを決めるのは利用する側なので、定義の説明として誤りになる。

## 8. 変更の経緯だけを説明するコメント（Whatコメント全般）を残さない

- コメントは「今のコードが何を・なぜそうしているか」を説明するためのものであり、「変更の経緯（前はこうだった → こう変えた）」を記録するためのものではない
- 経緯コメントが参照する旧実装・変数名・PR番号・issue番号が、現在のコードベース上のどこにも存在しない場合、そのコメントは将来の読者が検証しようのない情報になり、残す価値がない
- 経緯情報に限らず、コードを読めば分かることをそのまま日本語化しただけの「Whatコメント」も書かない。書くべきは「なぜ」（背景・制約・理由）
- 判断軸: 旧実装・旧値への言及を今のコードベースから消しても、コメントとして失われる情報が無ければ削除してよい。まだ検証可能な経緯情報（今も存在する設定値・関数への言及等）や、経緯以外にWhy情報を含むコメントは安易に削除しない

### NG例

```kotlin
// 以前は fetchLegacyAPI() を使っていたが、パフォーマンス改善のため fetchAPI() に変更
val result = fetchAPI()
```

↑ `fetchLegacyAPI()` が既にコードベースのどこにも存在しない場合、検証不能な情報。

### OK例

```kotlin
// レート制限(429)を指数バックオフで吸収するため、リトライ回数の上限を明示する
val result = fetchAPI(maxRetries = 5)
```

↑ 経緯ではなく、今のコードの挙動理由のみを書いている。

## 9. 作業をどう分割したかをコメントに書かない（PR・タスク相対の記述）

項目5 の兄弟。項目5 が「環境・運用の手順」を排除するのと同じ理由で、作業分割・進行状況の事情もコードの性質ではないので書かない。

- 「別PRで対応」「本PRの範囲外」「後続で置き換える」「一旦こうしておく」のような、PR / タスクという作業単位に相対的な記述を書かない。作業分割の事情は PR 説明・issue に置く
- 判断軸は項目5 と同じ形: 「コードが何をするか」＝書く / 「作業をどう分割したか・環境をどう設定するか」＝書かない
- 理由: 過去参照の経緯コメント（項目8）は参照先が消えて検証不能になるのに対し、作業単位への言及はその作業が完了した瞬間に記述そのものが嘘になるのに、コード側には何の変化も起きないので誰も気づかない。陳腐化の経路が逆向きなだけで、行き先は項目8 と同じ
- 公認の TODO は対象外: 「コードの望ましい最終状態」を述べる TODO（例: `EventID string // TODO: model.EventID を用いるように調整する`）は残す。禁止するのは未来への言及全般ではなく、「今回はやらない・別で対応する」という作業事情の語りだけ

### NG例

```go
DiscountRate: DefaultDiscountRate, // 割引率の判定は service 層が必要で別 PR 対応のため、暫定で通常の割引率
```

↑ 別 PR がマージされた時点で嘘になる。値がなぜ `DefaultDiscountRate` なのかというコードの性質は何も説明していない。

### OK例

```go
DiscountRate: DefaultDiscountRate,
```

↑ 作業分割の事情しか書くことが無いなら、コメント自体を書かない。

## 10. 設計の選択理由（代替案との比較）をコメントに書かない

「なぜ A ではなく B にしたか」は PR 本文・commit message に書く。コードコメントに残すと、B が当たり前になった後も A の話だけが残り続け、読み手に「まだ A が候補なのか」と誤解させる。

コメントに残すのは コードを読んでも分からない外部制約 だけ。「サーバーがこう振る舞うのでこの順序でなければならない」は残す。「SharedFlow ではなく StateFlow にした」は残さない。

### NG例

```kotlin
/**
 * 設定を読み直すべき回数を数えたもの
 *
 * イベント(SharedFlow)ではなく状態(StateFlow)にしているのは、
 * [getSettings] の購読が通知より後になっても取りこぼさないため。
 * 書き込みが待たされないので、通知元のスコープがキャンセルされても失われない
 */
private val settingsRevision = MutableStateFlow<Long?>(null)
```

### OK例

```kotlin
// nullはログインがまだ完了しておらず、設定を読んではいけないことを表す
private val settingsRevision = MutableStateFlow<Long?>(null)
```

同じ理由で、Flow の operator チェーンに operator ごとの注釈を付けない（`filterNotNull` の直前に「〜前は取得しない」等）。チェーン全体で 1 つ、外部制約がある箇所にだけ書く。

設計判断の根拠は PR 本文の「確認してほしいこと」に置く。

## 11. コメントは repo の既存コメントと同じ語彙・分量で書く

自分の語彙感覚ではなく、その repo の既存コメントを基準にする。どちらも機械的に確認できる。

### 語彙

日常的に使わない硬い漢語（「契機」「所以」「鑑みて」「企図」等）を避ける。判定は語のリストではなく repo 内の出現回数 で行う: `git grep <語>` して自分の diff 以外の出現が 0 件なら、その語はこの repo の語彙ではないので言い換える。

「遷移」のようにドメイン語として定着している語は出現回数で分かる（数百件あれば日常語、0 件なら非語彙）。

語尾も既存に合わせて統一する（「〜します」と「〜する」を 1 ファイル内で混在させない）。

### 分量

1 つの宣言に対する説明は、repo の既存 KDoc の分布に収める。数千件規模の repo でも中央値 1 行・p95 2 行程度で、5 行を超えるものは 1% に満たないことが多い。

長くなるのは、たいてい原則 10 の「設計の選択理由」が混ざっているサイン。書き終えてから分量を見て、超過していたら何が余分かを見直す。
