# GitHub PR Review

GitHub PR の変更内容を分析し、コードレビューを行う。例: `/review-pr 123`

手順の全体像:

| 段 | ステップ | 見るもの |
|---|---|---|
| 準備 | 1 / 2 / 2.2 | PR 情報・差分・Codex 並走 |
| 文脈 | 2.4 / 2.45 / 2.5 / 2.6 | PR スタック・過去のレビュー指摘・外部リンク・本文の裏取り |
| 前提 | 2.65 | この PR は要るか・この手段でよいか |
| 行 | 2.7 / 2.8 / 3 | チェックリスト・コメント品質・正しさ |
| 仕組み | 3.2 | 自前で持つ必要があるか |
| まとめ | 3.5 / 4 / 5 | Codex の採否・結果の出力・投稿文面 |

Codex 並走の注意点は `${CLAUDE_SKILL_DIR}/references/codex.md` にある。

## Instructions

### ステップ1: PR情報の取得

```bash
gh pr view <PR番号>
```

レビューは対象 PR の head のコードに対して行う（checkout するか、失敗したら `git show <headRefOid>:<path>` で読む。詳細はステップ3）。別ブランチのコードを根拠にしないため。

### ステップ2: 変更差分の取得

```bash
gh pr diff <PR番号>
```

### ステップ2.2: Codex レビューを並走させる

PR の head を worktree に取り出し、Codex の built-in review を background で投げてから、2.4〜2.8 を進める。回収はステップ 3.5。Codex は `~/.codex/AGENTS.md` と、そこから辿れる persona・各 guide の skill を自分で読むので、基準の指示文は渡さなくてよい。

```bash
read -r HEAD_OID BASE_REF <<< "$(gh pr view <PR番号> --json headRefOid,baseRefName --jq '"\(.headRefOid) \(.baseRefName)"')"
git fetch origin "pull/<PR番号>/head" "$BASE_REF"
SCRATCH=<この session の scratchpad の絶対パス>   # $TMPDIR は sandbox の内外で別の場所を指すので使わない
WT="$SCRATCH/review-pr-<PR番号>"
git worktree add --detach "$WT" "$HEAD_OID"
COMPANION=$(ls -d ~/.claude/plugins/cache/openai-codex/codex/*/scripts/codex-companion.mjs | tail -1)
node "$COMPANION" review --wait --cwd "$WT" --scope branch --base "origin/$BASE_REF" > "$SCRATCH/review-pr-<PR番号>.codex.txt" 2> "$SCRATCH/review-pr-<PR番号>.codex.log"
```

- 最後の `node` 行は Bash ツールを `run_in_background: true` で起動する
- worktree を作れない・Codex が動かない時は、この手順を飛ばしてレビューを続け、ステップ 4 の「外部レビュー」欄に未実施と理由を 1 行書く。回避策は探さない
- 終わったら `git worktree remove "$WT"` で片付ける（PR のファイルを `git show` で読む用途にも使えるので、ステップ 4 を書き終えてから）
- 失敗の型と出力形式は `${CLAUDE_SKILL_DIR}/references/codex.md`

### ステップ2.4: PR スタックの確認

差分を読む前に、その PR が単独か機能スタックの一部かを判定する。単独 PR として読むと、既に他 PR で解決済みの問題を指摘したり、逆に致命的な指摘の根拠を取り逃す。

```bash
# 同一機能の PR 群を洗う（タイトルの機能名・ブランチ名の接頭辞で検索）
gh pr list --search "<機能名>" --state all --limit 60 --json number,title,state,headRefName,baseRefName \
  --jq '.[] | "\(.number)\t\(.state)\t\(.headRefName) -> \(.baseRefName)\t\(.title)"'

# 同じ著者の open PR（ドラフト含む）。タイトルに機能名が無くても、本 PR の続き・作り直しはここに出る
gh pr list --author <PR著者> --state open --json number,title,isDraft,createdAt \
  --jq '.[] | "\(.number)\t\(.isDraft)\t\(.createdAt)\t\(.title)"'
```

著者検索で見つかった同領域の PR は、ステップ 2.65 の問 2（本 PR の追加分を後で捨てないか）の入力になる。

- `baseRefName` が既定ブランチ（develop / main 等）以外なら親 PR がある。逆に、この PR の `headRefName` を base にしている PR があれば子 PR がある
- 未マージの兄弟 PR が見つかったら `gh pr diff <番号>` を取り、最低限これを確認する:
  1. 同じ処理を先に実装していないか（重複追加・後で衝突する変更）
  2. 同じ問題をどう解いているか（エラー処理の方針・命名・レイヤー配置）。他 PR が採っている方針から本 PR だけ外れているなら、それは「既存との一貫性」の観点で強い指摘根拠になる
  3. 同じシンボルを重複追加していないか
- 衝突は推測せず実測する: `git merge-tree --write-tree <このPRのhead> <兄弟PRのhead>`。衝突した blob は `git cat-file -p <hash>` で中身を見て、自明な解決かどうかまで判定する
- reader / writer が別 PR に分かれている場合、片方だけ見て「このデータは存在しない」「この状態はあり得る」と判断しない。writer 側の実装（どういう条件でレコードを作るか）を読んでから結論を出す。writer が未マージなら、その指摘が「今の障害」か「writer マージ時に有効化する潜在バグ」かを区別して書く

レビュー本文には確認結果を書く（スタック図・本 PR の位置づけ・兄弟 PR との関係）。単独 PR だった場合も「スタックなし」と明記する。

### ステップ2.45: 過去のレビュー指摘を引く

同じファイル・同じ機能に、人が過去に付けた指摘を集める。人が一度見つけたパターンは同じ場所で繰り返されやすく、diff だけ読んでも「ここは前に問題になった」とは分からない。

対象にする過去 PR（合わせて 10 件程度まで。多ければ変更行数の多いファイルを優先）:

- PR 本文が言及しているマージ済み PR
- ステップ 2.4 で見つけた同一機能のマージ済み PR
- 変更ファイルを直近半年に触った PR

```bash
# 変更ファイルを直近半年に触った PR 番号（merge commit と squash の件名から拾う）
gh pr diff <PR番号> --name-only | while read -r f; do
  git log --since="6 months ago" --first-parent --format=%s "origin/<base>" -- "$f"
done | grep -oE '#[0-9]+' | sort | uniq -c | sort -rn | head -10

# その PR に人が付けた inline 指摘（bot と返信を除く）
gh api "repos/{owner}/{repo}/pulls/<過去PR番号>/comments" --paginate \
  --jq '.[] | select(.user.type != "Bot" and .in_reply_to_id == null) | "[\(.user.login)] \(.path):\(.line // .original_line)\n\(.body)\n"'
```

集めた指摘を 1 件ずつ今回の diff に当て、「同じ形が今回の diff にあるか」を判定する。同じ形があれば、過去の指摘（PR 番号とコメントの要点）を根拠に添えて指摘事項に入れる。その後の PR で直っているか・合意のうえ見送られたかは、コメントのスレッドを読んで確かめる。

レビュー本文には、見た過去 PR の番号と、当てはまった指摘の件数を書く。該当する過去 PR が無ければ「過去の指摘: 対象なし」と 1 行書く。

### ステップ2.5: PR 本文の外部リンクを読む

PR の `body` / `description` / `comments` に含まれる以下のリンクは、該当ツールで取得して内容を読む。リンクが本文に無くても、関連タスク・関連デザイン・関連仕様の記載があれば確認する。

- Notion リンク（`notion.so/...`, `www.notion.so/...`）
  - `mcp__notion__notion-fetch` でページ内容を取得する
  - タスク背景・受け入れ条件・仕様・関連 issue を読み、PR の変更が仕様と一致しているかをレビュー観点に取り込む
  - URL が見つからない / 取得失敗時は明示的に「Notion ページ未確認」と総評に書く
- Figma リンク（`figma.com/design/...`, `figma.com/file/...`, `figma.com/proto/...`）
  - URL から `fileKey` と `nodeId` を抽出（nodeId は `-` を `:` に変換）
  - `mcp__figma__get_design_context` で UI の構造・トークン・コンポーネント情報を取得する
  - 必要に応じて `mcp__figma__get_screenshot` でスクリーンショットも取得する
  - UI 系 PR の場合、デザインとの差分（余白・色・タイポ・コンポーネント命名）を必ず指摘候補に入れる
- その他リンク（Linear / Jira / Slack / GitHub issue 等）
  - 言及されていれば `WebFetch` か対応 MCP ツールで取得する。失敗したらその旨を総評に書く

外部リンクから得た仕様情報は「概要」「指摘事項」セクションで根拠として参照する（例:「Notion の受け入れ条件 2 に記載の〜が未実装」）。

### ステップ2.6: PR 本文の主張は裏取りする

PR 本文は著者の主張であり、それ単体ではレビューの証拠にならない。以下のいずれかに当てはまる場合、独立に verify してから判定に進む。

- A. 言い回し: PR 本文に「失われている」「lost」「missing」「巻き戻ってる」「regression」「元の挙動に戻す」「revert」「restore」「再実装」「re-add」「以前は〜だった」「previously」「used to」のいずれかが含まれる
- B. 過去 PR 番号への言及: PR 本文に過去マージ済み PR（`#NNNN` / `PR #NNNN` / GitHub PR URL）への参照が 1 つでもある。著者が「#NNNN ベース」「#NNNN を踏襲」のように中立的に書いていても起動する

理由: 「過去挙動の復元」を謳う PR の多くは正しいが、削除されたコードは後続 PR が意図的に消したものであるケースが混じる（リファクタで UX を意図的に変えた / 仕様変更 / 別バグの修正で削除された等）。鵜呑みにすると、その削除理由ごと巻き戻すことになる。

`regression-verifier` agent を Agent ツールで呼び出す:

```
Agent: regression-verifier
prompt:
symbol: <消えたと主張されているシンボル名>
file_path: <対象ファイルパス>
referenced_pr: <本文で言及されている過去 PR 番号（あれば）>
```

返ってきた verdict をそのまま判定に反映する:

- `incidental-deletion` → 復元 PR は妥当。通常レビューを続ける
- `intentional-deletion` → Must Fix として上げる
- `cannot-determine` → 総評に「リグレッション主張の裏取り未完了」と書き、判定を一段下げることを検討

### ステップ2.65: 問題設定の検問 — 「この PR はそもそも要るか・この手段でよいか」

ステップ 2.4〜2.6 の出力（兄弟 PR・過去の指摘・外部リンク・本文の裏取り）が揃った時点で、差分の行を読む前に答える。ステップ 2.7 以降は「この PR のやり方を前提に中身が正しいか」しか見ない。前提そのものを問う場所はここだけなので、ここを飛ばすと行レベルの指摘しか出ない。

PR 本文の how は著者が選んだ手段であり、それが最善かを問うのはレビュアーの責務。「趣旨は X のみ」と本文にあっても、X 自体の妥当性は問える。

以下 4 問に答える。各回答には前提レベルの根拠（下記）を添える。行番号は不要だが、ツール実行なしの推測は不可。

1. 目的に対して、repo は既に別の解を持っていないか — 同じ目的を他環境・他モジュール・他 OS がどう実現しているかを grep で確認する。本 PR だけが repo の既存パターンから外れているなら、それは persona の「既存との一貫性」をファイル間でなく環境間・レイヤー間に当てた強い指摘になる。repo の外にある解（標準ライブラリ・フレームワーク・依存済みライブラリ）は、PR の中の仕組み単位でステップ 3.2 が見る
   - 新しい UI 部品を足す PR では、既存のデザインシステム部品の拡張で済まないかを必ず確かめる。①Figma の `mcp__figma__get_metadata` で、その部品がどの既存コンポーネントのインスタンスから作られているかを見る ②差分の中に、既存部品と同じ形の判定・配色・寸法のロジックが無いかを grep する。どちらかが当たれば「既存部品に variant を足す形では足りないか」を問う
2. 兄弟・ドラフト PR が、本 PR の追加分を後で捨てないか — ステップ 2.4 で見つけた PR 群を読み、本 PR が入れる state・コード・データを次の PR が作り直す構成になっていないか確認する。そうなら本 PR は「一時的な中間状態」であり、その中間状態を経る必要があるかを問う
3. やらない・先送りする案は成立しないか — 「この PR を入れない / 後続 PR に統合する」で困ることを 1 つ具体的に言えるか。言えないなら、それを指摘として書く
4. この手段は何を固定するか — 一度入れると外しにくい前提（DB スキーマ・公開 API の形・IaC の state・命名・package の置き場所）を持ち込むなら、それが本当に今決めるべき前提かを問う

- 前提レベルの根拠として使えるもの: PR 本文の why/how の引用、兄弟 PR の本文・diff、他環境・他モジュールに対する grep 結果、Notion / Slack 等の外部リンクで確認した合意
- 使えないもの: 「一般的には〜が望ましい」だけの一般論、確認していない他環境の想像
- 書き方: 指摘は「〜という前提なら、この PR は不要 / 手段を変えるべき」の形で、前提を明示して出す。前提が確認できていないなら断定せず「〜であれば」の質問形で出す。確認したが問題が無かった場合も「前提・方針: 問題なし（確認した内容: …）」と 1 行書く。無言で通過しない
- 判定への影響: ここで指摘が立った場合、行レベルの検査が全件「問題なし」でも総合評価を Comment / Request Changes にできる。前提レベルの指摘を Nice to Have に落として Approve するのは、この検問の意味を失わせる

### ステップ2.7: 適用チェックリストの構築

repo 固有のルールを取りこぼさないために、行レベルの検査はチェックリストを元に行う。チェックリストは次の 2 つを合わせて作る。

#### (a) builder に作らせる

差分のファイル拡張子・変更内容から参照すべき skill を判断し、`review-checklist-builder` agent（Agent ツール）に渡す。available-skills に表示されている skill 名の中から、この diff に関係するものを選ぶ。

repo にガイドライン群（`docs/coding_guidelines/` 等）がある場合は、skill 名だけでなくそのファイルパスも渡す。AGENTS.md / CLAUDE.md にパス対応表があればそれに従って対象を選ぶ。渡す前にファイルパスの実在を自分で確認する（`ls docs/coding_guidelines/*.md 2>/dev/null || echo "NOT FOUND"`）。存在しないパスを渡すと、builder は「未ロード」と報告する代わりに一般論で埋めてくることがある。

```
Agent: review-checklist-builder
prompt: 以下の情報からレビュー適用チェックリストを生成してください。

作業ディレクトリ: <repo の絶対パス>

参照源1（ファイル / Read で読む）:
- <docs/coding_guidelines/*.md 等、対応表に従って選んだパスを列挙。無ければ「なし」>

参照源2（skill / Skill で起動する）:
- <available-skills から選んだ skill 名をカンマ区切りで列挙>

変更種別: <新規画面 / 機能削除 / リファクタ / API追加 / バグ修正 等>
変更ファイル概要: <gh pr diff --stat の出力>

各項目には出典（参照源名 + 見出し名 + MUST/SHOULD 区分）を必ず付けてください。
ロードできなかった参照源は「未ロードの参照源」に記載し、その分を一般論で埋めないでください。
```

使う前に実ファイル由来かを検める。以下のいずれかに当てはまるなら、builder はその参照源を読めていない:

- 出力末尾の「未ロードの参照源」に参照源が挙がっている
- 項目に出典が付いていない、または出典が参照源に実在しない見出しを指している
- 項目が一般論だけで構成され、参照源側の具体語（MUST / SHOULD 表記、固有のルール名、コード例の識別子、実際の関数名等）を含まない

その場合は未ロード分の参照源を自分で Read してチェックリストを補完し、レビュー本文に「builder が読めなかった参照源を自分で補完した」と明記する。

#### (b) diff の語で guide を引く（自分でやる）

builder は diff 本体を見ず、大きい references は読み切れない。diff に出てくる語から該当項目へ辿る経路は builder には無いので、ここは必ず自分で行う。

1. diff の追加行から、API 名・型名・プロパティ名・オペレーター名を拾う（例: `currentUser`、`take(1)`、`repeatOnLifecycle`、SDK のメソッド名、既存部品の名前）。import と呼び出しを見れば 10〜20 語に収まる
2. その語で、(a) で選んだ skill の本体と `references/` を grep する

```bash
# 自分で置いた skill は ~/.claude/skills/<skill名>、この plugin に同梱の skill（code-quality-principles 等）は ${CLAUDE_SKILL_DIR}/../<skill名>
SKILL_DIR=~/.claude/skills/<skill名>
grep -rn -F -e '<語1>' -e '<語2>' "$SKILL_DIR"/ | cut -c1-200
```

3. 当たった項目は見出しごと読み、チェックリストに足す。出典は「skill 名 + 項目番号」

当たりが 0 件でも「diff の語で guide を grep: 該当なし（引いた語: …）」と残す。

### ステップ2.8: コメント品質の検問

`code-comment-cleanup` skill を Skill ツールで呼び出す。`mode=detect-only` を必ず明示する（Edit させない）:

```
Skill({skill: "code-comment-cleanup", args: "target=PR<PR番号> mode=detect-only min_confidence=medium"})
```

この diff に検証不能な経緯コメント・What コメント・根拠不明の推測・運用手順の混入・実装値の写経が無いかを機械的に検出させる。返ってきた項目は確信度に応じてステップ 4 の指摘事項に振り分ける（高確信度 → Should Fix 目安、中確信度 → Nice to Have 目安）。検出ゼロならその旨を「適用チェックリスト結果」の近くに一言添える。

### ステップ3: レビューの実施（チェックリスト消化）

ステップ 2.7 のチェックリストを 1 項目ずつ差分に当てて消化し、各項目を `該当・問題あり` / `該当・問題なし` / `非該当` で判定する。`該当・問題あり` の項目はステップ 4 の指摘事項に展開する。

- 判定の前に根拠を作る（MUST）: 各項目の判定は、この会話内で実際に実行した `Read` / `Grep` / `Bash`（`gh pr diff`, `git grep` 等）の結果に基づく。ツールを実行せず記憶や推測（「〜のはずだ」「一般的には」）だけで判定しない。項目ごとに、判定の根拠（参照したファイルパス・行番号、実行した grep コマンドと出力、または diff 中の該当箇所）を最低一行添える。根拠を示せない項目は `未検証` とし、その旨を総評に明記する
- ブランチ切替が失敗したまま `Read` / `git grep` の結果を証拠にしない（MUST）: `git checkout` / `gh pr checkout` は `.git/config` が書き込み不可な環境で失敗しうる。失敗した場合、working tree 上の `Read` / `git grep` は別ブランチのコードを見ている可能性がある。指摘を書く前に、対象ファイルが `gh pr diff <PR番号> --name-only` の出力に含まれることを確認する。切替に失敗した場合は、ファイル内容の確認を `git show <headRefOid>:<path>`（`gh pr view <PR番号> --json headRefOid` で取得）に切り替える

その上で、チェックリストに載らない正確性・セキュリティ・性能・テストの欠落も見る。次の 2 つは、該当する箇所があれば必ず行う。

- 一度だけ確定する値は、出どころまで辿る: 最初の 1 件で確定する処理（`take(1)` / `first()` / 初期値のまま使う状態 / コールバックやクロージャに閉じ込めた値）を見つけたら、最初に流れてくる値が何か（ディスクキャッシュ・null・初期値・API の応答）を供給元の実装まで読んで確かめる。そのうえで「その値で確定してよいか」を仕様と照らし、「後から値が変わった時に追従するか」を確かめる。「キャッシュで足りる」「初期値で問題ない」と判定する時は、その値が古い・空の時に画面で何が起きるかを 1 行書く
- 分岐を持つロジックは、テストに無い入力を手で流す: 入力の形で結果が変わる処理（並べ替え・グルーピング・表示条件の判定）は、追加されたテストケースの入力を確認したうえで、テストに無い形（先頭や末尾が空・同じ状態が連続する・0 件・1 件）を 1 つ選び、コードを手でなぞって出力を出す。仕様（Notion・Figma）にその形の記載があれば照合し、無ければ「この入力の時の期待値」を質問として出す

正しく動くが重い書き方かどうかは、次のステップ 3.2 で見る。

### ステップ3.2: 仕組みの検問 — 「この仕組みを自前で持つ必要があるか」（MUST）

ステップ 3 は「書かれたコードが正しいか」を見る。ここでは「正しく動くが、もっと軽い既存の解で書けないか」を見る。ステップ 2.65 が PR 単位で手段を問うのに対し、ここは PR の中の仕組み単位で問う。規約由来のチェックリストにも Codex にも出てこない観点なので、ここを飛ばすと「正しい自前実装」を素通しする。

1. 仕組みを列挙する — diff が新しく持ち込む仕組みを書き出し、それぞれの行数（コメント込み）を数える。仕組みとは、状態を持つクラス・ホルダー、アニメーション・ジェスチャ・キャッシュ・リトライ・並行制御・同期の自前処理、描画・パース・変換の計算のこと
2. 仕組みごとに既存の解を探す — 探す順は、標準ライブラリ・フレームワーク → repo が既に依存しているライブラリ → repo 内の共通実装。repo 内の grep だけで終えない。Android は `android docs search <やりたいこと>`、それ以外は公式ドキュメントを「やりたいこと」の語で引く。見つけた候補が repo で使えるか（BOM・バージョン・opt-in の要否）は、repo 内の既存利用の grep か依存のバージョンで確かめる
3. 自前にする理由を確かめる — 標準では満たせない仕様値や、既存部品の制約があるなら、自前が正しい。理由を 1 行で言えないなら指摘候補にする
4. 兆候があれば必ず 2 を実施する — 次のどれかがある仕組みは、フレームワークと戦っている可能性が高い:
   - 同じ PR の中に、その仕組みの不具合を直す commit がある（`git log origin/<base>..<head> --oneline` で「〜中に〜すると飛ぶ」「〜の間に〜すると」等を探す）
   - 読み取り追跡の回避や、フェーズをまたいで共有する可変状態がある（例: `Snapshot.withoutReadObservation`、`SideEffect` での可変ホルダーへの書き込み、composition・layout・draw・input で同じオブジェクトを読み書きする）
   - 実行順序やタイミングを説明する長いコメントがある（「〜が残っている間に控える」「最初のフレームでは〜なので」）
   - ファイルのコメント行の割合が repo 全体の平均を大きく超える

- 書き方: 結果は「仕組み / 行数 / 既存の候補 / 判定（置き換え可・自前が妥当（理由）・未確認）」の表にする。候補が見つからなかった仕組みも行を残す（無言で通過しない）。置き換え案は、試していなければ質問形で出し、代替コードは「イメージ」として示す。同じ動きになるかを確かめていないことと、差が出そうな点（途中での中断・非表示中の変更・アクセシビリティ等）を添える
- 判定への影響: 置き換えで数十行以上の仕組みが消える指摘は Should Fix が目安。同じ PR の中に fix commit が積まれている仕組みなら、総合評価を Comment 以上にする根拠になる

### ステップ3.5: Codex レビューの回収と採否

ステップ 2.2 で投げた review を回収する。まだ終わっていなければ終了通知を待つ（15 分で打ち切り、未実施扱い）。

```bash
cat "$SCRATCH/review-pr-<PR番号>.codex.txt"
```

`[P0]`〜`[P3]` の行ごとに、自分のステップ 3 の判定と突き合わせてから扱いを決める。Codex の finding をそのまま Must / Should に書かない。

- 自分も同じ箇所を問題ありと判定していた: 根拠を合わせて指摘事項に書く（Codex の指摘である旨は不要）
- 自分は見ていなかった箇所: Read / grep で裏を取り、成立すれば指摘事項に加える。成立しなければ「外部レビュー」欄に「見送り: 理由」で残す
- 裏が取れない: 「未確認」として「外部レビュー」欄に残す。指摘事項には入れない

ユーザーが「Copilot でも」「3 つ目の目で」と言った時だけ、`copilot-reviewer` agent を Agent ツールで呼ぶ（cwd は 2.2 の worktree、scope は `base=origin/<baseRef>`、scratch は同じ scratchpad）。返ってきた指摘も上と同じ 3 分類で扱い、「外部レビュー」欄に Codex と並べる。既定では呼ばない（二重に採否する手間が増えるため）。

### 概要
[PRの目的と変更内容の要約。Notion等から得た背景情報があればここに反映]

### ステップ5（任意）: GitHub へ投稿する文面の下書き

ステップ 4 の形式は chat 向けの報告形式であり、GitHub にそのまま貼らない。ユーザーが「コメントして」「投稿する文面にして」と求めた場合は、投稿文面用の skill があれば Skill ツールで呼び出し、無ければ 1コメント1論点・語尾で強度を表す・根拠を添える形に変換して下書きを提示する。投稿（`gh pr comment` / `gh pr review`）は通知が飛ぶ外部への発信なので、ユーザーの明示承認の後。

## Notes

- PR が大きい場合は、重要なファイルから順にレビューする
- プロジェクトの CLAUDE.md がある場合は、その規約に従ってレビューする
- 正しく動くことと、その書き方でよいことは別の問い。行レベルの検査が全件「問題なし」でも、ステップ 3.2 で仕組みごとに標準 API・依存済みライブラリの解を探すまでレビューは終わらない
- ビルド・テスト実行はレビュアーの仕事ではない。ビルドエラーとテスト結果は CI が検証する。レビュアーがすべきことはコードリーディング・grep・手計算による論理検証であって、`gradle`・`xcodebuild`・`go test` 等を手元で走らせるのは役割の重複になる
